# Design decisions

Every real choice in this project: the options considered, the choice, and the evidence behind it
(each number names the command and the results file that produced it). IDs (R1, C1, ...) are stable
references used in code comments, so they are not renumbered.

- **R rows** are the domain rules set by the author (Ron Salama). R3 is retired: it recorded the
  project's framing (general financial-document AI), which is not a data rule; the ID is not reused.
- **C rows** are design and evaluation choices made while building with Claude Code (see the README,
  "How it was built").

- **Decided**: settled; changing one would change the data contract, the labels, a safety rule or
  how a result is measured.
- **Defaults to revisit**: working defaults picked on reasoning or a small sample, each with the eval
  that will settle it.

## Decided
| # | Choice | Options | Decision and why |
|---|---|---|---|
| R1 | Invoice totals | one total / two totals | Invoices get TWO totals: `total` (this invoice's own charges) and `amount_due` (overall owed, may include an old balance). Keeps both numbers a lender needs, and the math check (subtotal + tax = total) still works. |
| R2 | Reading numeric dates | month/day/year / day/month/year | Numeric dates in these (all US) documents are read month/day/year; the SAME rule is in the labels and in the extraction prompt. 9/10/2020 is ambiguous; grader and model must follow one rule or the score is meaningless. |
| R4 | Invoice `bill_to` | the customer being billed / the "Ship To" (delivery) name | Invoice `bill_to` = the customer being billed ("Bill To" / "Sold To" / "Customer name"): for a company, the company name, not an attention line or department; for an individual customer, the person's name; never the "Ship To" / delivery name. Refined 2026-10-04: the first wording ("the customer COMPANY ... never a person") was wrong for `inv_sammy`, whose customer is a person, and the model took the Ship To name "Taylor's Store" instead (baseline `evals/results/extraction_20261002-1913.json`). Same text in `schemas.py` and `data/labels/LABELING_GUIDE.md`. A lender cares who owes the money. Matches how commercial invoice extractors split "customer name" from the billing recipient. |
| R5 | Field names | industry abbreviations (`noi`) / readable names | Readable field names: `net_operating_income` (not `noi`), `cap_rate_percent`, `fixed_rate_percent`, `spread_percent`, `building_area_sq_ft`. Code should read clearly to humans; the industry abbreviation (NOI, cap rate) is kept in each field's description, which the model also reads. |
| R6 | Appraisal building area | gross / net rentable area | Appraisal `building_area_sq_ft` = the GROSS building area when both gross and net rentable area are printed. Gross was chosen on the first appraisal labeled; one fixed rule keeps labels and model consistent across documents. |
| C2 | Numbers extracted "as printed" + a `units` field; scaling done in code | ask the model for full dollars / as printed | As printed: we never ask the LLM to do arithmetic. |
| C3 | Every extracted value needs a verbatim evidence quote that code finds in the text | no evidence / evidence only | Cheap, code-only hallucination check; reviewers see where each value came from. Since 2026-10-04 the quote must also CONTAIN the value (C22), and a table header split over several lines is accepted (C23). |
| C4 | Retry policy | 1 / 3 / 5 attempts | 3 attempts: invalid JSON -> retry with the error; rule problems -> retry, then human review queue. Since 2026-10-04 a retry re-asks only the failing fields (C24). |
| C9 | Cited-answer rules (`ragagent/rag/answer.py`) | k = 3 / 5 / 10; answer with no real citation: refuse / show with a warning; invalid JSON from the LLM: refuse / retry | k=5; made-up citation numbers are removed and the answer says so; an answer left with no real citation is refused; invalid JSON is refused, not retried (1 LLM call per question keeps us inside the free quota). Fail closed: for a lender "I don't know" beats an untraceable answer. |
| C13 | Agent's `extract_fields` tool (`config.AGENT_EXTRACT_TOOL`) | always on / off until the hand labels are finished / never give the agent this tool | On by default (`AGENT_EXTRACT_TOOL=1`), since all 15 hand labels are finished. The switch exists so that model output is not shown while a document is being hand-labeled (it would bias the label); set `AGENT_EXTRACT_TOOL=0` in `.env` while labeling new documents. Each call costs 1-3 extra LLM calls (C12). |
| C14 | Retrieval eval: what counts as a hit, which k (`evals/retrieval_eval.py`) | hit = right doc AND one of the expected pages / the chunk must also contain the golden quote / right doc only; k reported 1/3/5 or 1/3/5/10; MRR cut-off 5 / 10 | Page-level hit is the main number (pages are what we cite, and it does not depend on the chunking, so chunk sizes can be compared), plus quote@5 as a stricter check because page hits favour big chunks. hit@1/3/5/10 (3/5/10 = the k options in C9) and MRR@10; answerable questions only. Numbers, all on the 24-question DRAFT golden set (drafted by Claude Code and verified against the source text page by page, see `evals/GOLDEN_README.md`), 2026-10-01 17:50, after the Part 4 review corrected two draft answer-key entries (a19 listed 1 of the 4 pages that answer it and used the appraisal's outlier carport count; a21 missed p.106): `python -m evals.retrieval_eval` (Chroma) hit@1 58%, hit@3 79%, hit@5 83%, hit@10 92%, quote@5 83%, MRR@10 0.698; `--exact` gave identical numbers (no HNSW miss on these questions, C10). `python -m evals.retrieval_eval --ablation` (exact search; hit@5 / quote@5 / MRR): 400/0 88% / 62% / 0.752, 400/80 88% / 58% / 0.730, 800/0 88% / 83% / 0.732, 800/150 83% / 83% / 0.698, 1600/0 83% / 83% / 0.699, 1600/320 79% / 79% / 0.672. (Before that correction a19 counted as a miss at every setting, which cost each metric up to 1 question - a wrong answer key looks exactly like a retrieval failure.) The gaps are 1-2 questions of 24 (1 question = 4.2 points): noise, not a winner. What IS clear: 400-char chunks often split the needed passage (quote@5 58-62%); 1600-char chunks overflow the embedder's 512-token input (120-143 chunks cut); a20/a22 (zoning/parking in the long appraisals) miss at EVERY setting, so chunk size is not their fix (ideas: document name inside each chunk, keyword/hybrid search, a reranker). Overlap 0 first needed a one-line fix in `chunk.tail` (`text[-0:]` is the whole text). Re-run on the extended, hand-written golden set before deciding C6. |
| C16 | Answer-eval counting rules (`evals/answer_eval.py`) | refusal on an answerable question: counts as wrong / is left out; a trap answered with "not in the documents": counts as a refusal (judge decides) / only code refusals count; agent `needs_human_review`: refusal / own category; LLM error: refusal / own category | A refusal on an answerable question is a false refusal and NOT correct (else refusing everything would look perfect). Trap refusal accuracy = code refusals + answers the judge says only declined. Agent `needs_human_review` hides the answer, so it counts as a refusal (and is also counted as "flagged for human review"); an answer without a citation = refusal (C9); errors are counted on their own, never as refusals. Smoke runs 2026-10-01, plain RAG, NOT reportable (`--ids t01,t04,t06` and `--limit 5`): 3/3 traps refused by gate 2 although all passed gate 1 (best scores 0.71-0.75, cf. C8); 5/5 easy invoice questions correct, faithful and citing the expected page, as judged by the LLM judge, not by a person (those 5 rows are in `evals/judge_calibration.csv`, still with 0 human verdicts). |
| C17 | Docker image contents (`Dockerfile`) | embedding model AND Chroma index built into the image at build time / image holds code only, model + index on mounted volumes / build the index when the container starts | Built in at build time: the container starts with no internet except for the LLM and no setup step, the CI smoke test is repeatable, and a reviewer runs ONE command. Costs: the model (~130 MB) is inside the image, any change to `ragagent/` or the data re-runs ingest during the build (93.5 s locally, C7), and new documents mean a rebuild. Also: CPU-only torch 2.14.1 installed before `requirements.txt` (the default Linux torch pulls CUDA, ~3 GB of downloads per the 2026-09-30 research); `HF_HUB_OFFLINE=1` after the model download, so a model-name mismatch fails the BUILD instead of downloading at run time; non-root user `app`; `GEMINI_API_KEY` only at run time (`--env-file .env`), never in the image; `python:3.13-slim` (same Python as the venv). Checked 2026-10-01 without Docker: all 116 packages resolve to Linux wheels for Python 3.13 (`pip install --dry-run --platform manylinux_2_17..2_41_x86_64 --python-version 3.13 --only-binary=:all: -r requirements.txt torch==2.14.1+cpu`). Built only in CI so far (Docker is not installed on the development machine). Measured in the first CI run (2026-10-04, run 37205328703): image 1.96 GB, image build ~5.5 min (~6 min for the whole job) on a GitHub runner, smoke test 3/3 and 153/153 self-test cases inside the image with the network off. |
| C18 | What CI checks (`.github/workflows/docker.yml`) | build only / build + `GET /health` / + `/documents` + an off-topic `/ask` (refused by gate 1, no LLM) + every offline `--selftest` inside the image with `--network none` / + a live answer eval with the key as a GitHub secret | Everything except the live eval: needs no secret and no LLM quota, proves the model and index are really inside the image and work offline, and runs every offline self-test module (including the three core loops) on every push. A live eval would spend free quota on each push and store the key on GitHub. Triggers: push to `main`, pull requests, manual button; docs-only changes skipped. Before the repo was on GitHub (2026-10-01), the 14 self-test modules of the time passed in the venv and `scripts/smoke_test.py` passed 3/3 against a local `uvicorn`. First CI run 2026-10-04 (run 37205328703): green, all 15 modules (153/153 cases) inside the image with `--network none`, smoke test 3/3. Part 5 review (2026-10-01): a module also fails CI when its "N/N passed" line is missing (before, a self-test that never ran - e.g. a usage text printed instead - passed silently); the self-test loop copied from `docker.yml` passed all 14 modules against a copy of the image's files (see `docs/DOCKER_SETUP.md` section 9). |
| C19 | Re-downloading `data/raw` (`ragagent/download.py`) | pause before each request 0.2 / 1 / 2 s; a file that already exists: skip / always re-download / compare a checksum; who gets your `SEC_USER_AGENT` (name + email): every site / sec.gov only | 1 s pause (SEC allows 10 requests/s; 15 files take ~15 s anyway); skip existing files (re-runs cost nothing); no checksum yet (`manifest.csv` has no hash column; one would catch a document that changed upstream). SEC User-Agent only from the env var `SEC_USER_AGENT` (name + email), never in code; a .pdf that does not start with `%PDF` (an error page) is rejected. Checked 2026-10-01: `--selftest` 12/12, `--dry-run`, and one real download (a 15 KB non-SEC PDF into a temp folder) byte-identical to the committed copy. Part 5 review (2026-10-01): the name + email went to EVERY site when set; now sec.gov only, other sites get the generic User-Agent (they don't ask for an identity). `--selftest` 13/13; all 5 non-SEC documents re-downloaded into a test folder with the generic User-Agent, byte-identical to `data/raw`; the sec.gov path is covered by the self-test only (no live SEC request made in the review). |
| C21 | Labeling rules found while labeling loans/appraisals (same text in the labels guide and in the schema descriptions the model reads) | a stepped rate as 'fixed' + starting rate / as 'unknown'; a use outside the list as 'other' / nearest list item | Stepped rate that is set in advance (JS Highland: 10%, +2% a year from year three) = `fixed` with the STARTING rate: it never follows a market index. A building whose use is not in the list (Hallandale: auto body repair, "Commercial") = `other`. |
| C22 | Value-in-quote check (`ragagent/extract.py`, `check_rules` step 1b) | the quote only has to exist in the document (before) / the value must also be printed IN its own quote | The value must be in its quote. Why: in the baseline (`evals/results/extraction_20261002-1913.json`) `inv_contoso_stmt6` got tax = 311.25, which the model worked out from "Sales Tax 3%" and "backed" with that real quote, so it passed as `ok`: the only false fill (hallucination) of the run. How: numbers are read from the quote (commas, `$`, `%`, "1.2 million"; "0.5" is one number, so 5 never matches it); the sign counts only in financial statements, where "(25,202)" = -25202 (a loan note prints a positive "($100,000,000.00)"); dates are found in the common printed forms ("June 30, 2026", "6/30/26", "2026-06-30", "1st day of April, 2020"); `period_months` is skipped (printed as words: "Three Months Ended"). Checked offline first: run on the cached model answers of all 15 documents, it flagged only that tax. After (`evals/results/extraction_20261004-1530.json`): tax = null, no calculated value; the document is `needs_review` (C5). |
| C23 | Header-tolerant quote check (`ragagent/extract.py`, `_quote_in_text`) | exact match only (before) / the quote's words in order anywhere within 300 characters / in order, where the only jump allowed is to the FIRST word of a later line, within 300 characters | The last one. Why: tables are flattened to text, so the column header "Three Months Ended" / "June 30," / "2026" sits on three lines, and the model's quote "Three Months Ended June 30, 2026" failed the exact check: in the baseline Omega and NHI went to review although the value was right. The "anywhere in order" version, tried first, also accepted a number from the next column of the same row ("Total revenues 282,506" = Omega's prior-year revenue, row "Total revenues \| 328,246 \| 282,506"), so jumps are allowed only to a new line, and a number is one word ("121" is not part of "121,319"). Known limit: it checks words and lines, not table columns. After (`evals/results/extraction_20261004-1530.json`): Omega and NHI `ok` on the first attempt. |
| C24 | What a retry may change (`ragagent/extract.py`, `extract_with_retries` + `keep_passed_fields`) | re-ask the whole form and take the new answer (before) / re-ask only the fields a problem names and keep the rest | Only the failing fields. Each problem names its field(s) (a broken business rule names every field in it); the retry prompt lists them and says the other fields are final; code then takes ONLY those fields from the new answer, so a retry cannot change a field that passed, whatever the model says. Why: in the re-run of 2026-10-02 19:28 (`evals/results/extraction_20261002-1928.json`) a retry asked for one date quote and the model also swapped Omega's correct FFO (223,963) for AFFO (261,357). Also: `attempts` = how many times the model was really asked (the self-test checks it against the fake LLM's call count), and a valid answer followed by invalid JSON now ends in `needs_review` with that valid answer instead of `failed`. Self-test (`python -m ragagent.extract --selftest`): the 5 old cases + a retry that tries to change a passed field (kept) + a calculated tax (caught; fixed or sent to review) + 10 checks of the quote helpers = 18/18 (2026-10-04). After: Omega's FFO is right again (attempt 1 now passes, so no retry happens). |
| C25 | Address grading (`evals/score_extraction.py`, `same_address`) | text similarity, like names (before) / compare the parts: street number + name, city, state, ZIP | Parts. State names = abbreviations (California = CA), a county part is ignored, Parkway = Pkwy; city, state and ZIP are compared only when both sides print them; no fuzzy match (the 85% similarity rule calls "1228 Rossmoor Pkwy, ..." and "1229 Rossmoor Pkwy, ..." the same). Why: `appr_valleyview_alf` "..., Walnut Creek, CA 94595" vs the label "..., Walnut Creek, Contra Costa County, California 94595" was graded wrong though both are right. Grader self-test: `python -m evals.score_extraction --selftest` 10/10. Re-grading the baseline's own label/prediction pairs (`python -m evals.score_extraction --rescore evals/results/extraction_20261002-1913.json` -> `evals/results/extraction_20261004-1529_rescore_of_extraction_20261002-1913.json`) changed only that field: 126/131 -> 127/131. So 1 of the points gained since the baseline is a grader fix, not a better pipeline. |
| C26 | How Part 1 results are reported | one run / one run + re-runs of the changed documents with the disk cache off (`python -m evals.extraction_variance N doc ...`) | One scored run + re-runs, because Gemini 3.5 ignores `temperature` and one run can be luck. 2026-10-04 (labels unchanged since the baseline; same model `gemini-3.5-flash-lite`): baseline 126/131 = 96.2%, false fill 1/18, 13 `ok` + 2 `needs_review` (`extraction_20261002-1913.json`) -> same predictions, new grader 127/131 = 96.9% (C25) -> after C22-C24 + the R4 wording, new run 128/131 = 97.7%, false fill 1/18, 14 `ok` + 1 `needs_review` (`extraction_20261004-1530.json`; 6 live LLM calls, the other 11 documents replayed from the disk cache). Fixed: stmt6 tax (C22), Sammy `bill_to` (R4), Omega/NHI false reviews (C23). New: `inv_capozzi_legal` `amount_due` = 165.00 (label null; the model read "Total Fees & Disbursements" as an amount-due line). Re-runs, 3 each, cache off (`extraction_variance_20261004-1532.json`, 15 LLM calls): Sammy `bill_to` right 3/3, stmt6 tax null 3/3 (`needs_review` 3/3), Capozzi `amount_due` right only 2/3: run-to-run variation, not a fix or a break. Still wrong, same cached answer as in the baseline (not re-run): `fs_sfr_fy2025` `net_income` (the model took plain "Net income" 33,306; the label is the "Net income attributable to common stockholders" line, 7,575, as the schema asks) and `appr_hallandale_comm` `property_type` (industrial vs other, C21). |
